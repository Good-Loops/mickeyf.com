# Registration and browser Apple activation contract

This source prepares new account creation and Apple browser authentication. All new capabilities stay closed without exact operator opt-ins. These instructions are not approval to change provider settings, SQL, credentials, traffic or signing profiles.

## Registration

`REGISTRATION_ENABLED` enables the shared password/provider preflight only at the exact value `true`. `REGISTRATION_POLICY_REVIEWED` must separately be exactly `true`. `REGISTRATION_POLICY_VERSION` identifies the reviewed policy. `REGISTRATION_COUNTRY_RULES` is a JSON object whose uppercase two-letter country keys each contain exactly one integer `parentRequiredBelow`, between 1 and 18. There are no built-in jurisdiction rules. Configuration requires owner review of the actual countries, age thresholds, consent method and rollout scope.

The page collects country and a coarse age range before email, password or provider credentials. It does not request a birth date or infer age from a provider or network location. Unknown countries are unavailable. The parent-required range and explicit parent/guardian entry lead to an unavailable parent-led registration boundary until a reviewed verification and consent workflow exists; a checkbox cannot bypass it. The adult range starts at 18 as a product privacy boundary, not a legal conclusion.

One signed anonymous cookie binds a five-minute SQL authorization shared by password and provider signup. A changed policy digest, expiry, reuse or different cookie rejects it. Profile insertion and grant consumption commit in the account-creation transaction. Duplicate account failures roll back consumption. Provider identities match verified provider subjects; matching email does not automatically link accounts.

New minor profiles have private scores. Public leaderboard filtering happens before ordering/limits. Existing unclassified accounts retain their previous visibility. Profile rows cascade on account deletion. Registration pause does not hide existing provider login or disable password login.

`0019_create_registration_authorizations.sql` and `0020_create_account_registration_profiles.sql` require explicit migration approval and scoped runtime grants. Startup verifies their exact schema/history even while registration is paused because leaderboards read the profile table. The separate `registration-apply` migration command selects only these effects; ordinary migration commands do not implicitly activate them. Never repeat previously applied migrations; obtain a fresh checksum and target plan first.

Grant expiry invalidates authorization immediately; it is not a physical-retention guarantee. Begin requests opportunistically remove up to 100 expired grants. Trusted cancellation removes only that unconsumed anonymous grant and never logs out a newly authenticated account. Protected maintenance independently removes at most 1,000 expired rows per invocation and reports backlog/failure. Production activation requires a verified maintenance cadence, capacity, retention acceptance and failure/backlog alerts, including behavior during Apple outages. Retaining coarse country/age profile data for account lifetime also requires owner policy review.

## Browser Apple

`APPLE_WEB_AUTH_ENABLED` is a separate exact-`true` issuance flag. `APPLE_WEB_SERVICES_ID` must be a distinct Services ID associated with the existing primary native App ID. `APPLE_WEB_REDIRECT_URI` is one exact, canonical HTTPS domain URL without query, fragment, user info, explicit port, IP address or localhost. Configure both together. The backend owns the URL; requests cannot override it. Keep these identifiers configured when issuance is paused so queued web credentials and server notifications remain processable.

The frontend loads only Apple's published JavaScript SDK and uses `usePopup: true`. The SDK receives `clientId`, exact `redirectURI`, `state`, `nonce` and `scope: email`. The callback is the SDK promise using Apple's `web_message` response; this implementation does not receive credentials through a form-post or URL route. The configured return URL must still be registered with Apple and supplied unchanged to the server code exchange. Using the existing `/login` page needs no new credential-handling HTTP endpoint.

After loading the SDK, a real click opens its popup. This extra click preserves browser user activation. Blocking, dismissal, timeout, navigation and cancellation reject safely. A cancelled outstanding SDK popup prevents another popup until its promise settles; if the provider never settles, reload is required. Late responses cannot authenticate a cancelled operation. The SDK validates Apple's message origin, the client validates state, and the backend consumes the cookie-bound one-use attempt before validating signatures, exact audience, nonce, issuer, time and subject on both ID tokens. The optional unsigned `user` object is discarded. Tokens stay in memory and HTTPS request bodies, never URLs, browser storage or logs.

Native exchange continues to omit `redirect_uri`. Web exchange includes the configured URL. Client secrets use each exact client ID. Encrypted refresh tokens bind account, token ID, client ID and key ID as authenticated data; a native vault rejects a web row. Storage chooses the repository from the cryptographically verified audience. Deletion marks all account credentials for revocation. Workers route each row to its exact client, retry uncertain failures without extending retention, and purge expired rows independently of Apple/keys. Unknown audiences cannot be silently treated as successful revocations.

Browser issuance requires runtime-secret loading, token lifecycle, notifications, protected maintenance and account deletion prerequisites. Apple signup additionally requires explicit Apple deletion; all signup also requires registration preflight. A secret-loading outage hides Apple capability and leaves Google and independent cleanup available. Provider notifications accept configured native and web audiences even while new issuance is paused.

`APPLE_SIGN_IN_PRIVATE_KEY_SECRET_VERSION` and `APPLE_TOKEN_ENCRYPTION_KEYS_SECRET_VERSION` must pin approved numeric versions. `APPLE_SIGN_IN_TEAM_ID`, `APPLE_SIGN_IN_KEY_ID` and `APPLE_TOKEN_ACTIVE_KEY_ID` are public configuration identifiers. Never commit private key or encryption JSON values. The existing runtime identity receives only approved secret-resource grants; the receipt worker does not need Apple secret access.

## Rollout gates

Review the exact Services ID/domain/return URL before provider creation. Notification registration is a separate action after the receiver is deployed and controlled delivery is verified. Refresh only the existing iOS provisioning profile with its existing distribution certificate through the approved secure flow; do not generate replacement certificates or Apple keys incidentally.

Before rollout, validate one immutable source snapshot across backend/frontend tests and builds, disposable SQL, native route tests, unsigned Android build/lint and unsigned iOS compile. Prepare fresh production schema/grant plans, candidate and compatible rollback image digests, pinned session secrets, scan evidence, current server identity and a concrete traffic plan. Do not consider prior-revision native CI evidence validation of new source. Registration remains closed until its policy and operational retention gates are reviewed. Android provider activation additionally requires a real release signing identity; no Play account or certificate is assumed.

After any new private profile exists, a rollback must retain profile-aware leaderboard filtering. A historical image that ignores the profile table can expose a minor's scores. The rollback must also preserve shared registration authorization or keep every account-creation route disabled, retain schema/session compatibility, and continue queued Apple token revocation and notifications. Pausing new signup or provider issuance does not remove these obligations. Verify these properties against the exact rollback image before accepting traffic changes.
