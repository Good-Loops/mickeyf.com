# Parent-managed child activity: inactive foundation

This is source preparation only. The writer has no production runtime wiring or enable flag, and the draft SQL is outside the migration manifest. Nothing here applies a migration, backfills an existing account, sends a warning or deletes data. Good-Loops and other ordinary accounts do not acquire activity rows.

The proposed three-calendar-year inactivity policy cannot be enforced from session timestamps, which expire and can be deleted on logout. The draft `parent_managed_child_activity` table records one UTC timestamp, without a behavioral history. Its foreign key limits rows to current parent-managed child relationships and cascades when that relationship is removed. The writer initializes a row in the child-creation transaction and updates an existing row, in the same transaction as a successful interactive password sign-in. Missing rows remain missing; existing accounts are not treated as inactive. No provider login, session renewal, score submission or guest play is recorded by this foundation.

The design is deliberately conservative: a failure to write the enabled activity record rolls back the associated new child or password session transaction. Runtime wiring must only be considered after the exact schema and least-privilege grants have been independently reviewed and verified against the target, and compatible rollback behavior is established. Enabling it requires a separately reviewed rollout and cannot make statements about historic activity.

A timestamp alone does not implement the owner's rule. Before publication or enforcement, define which account actions count as activity, whether authenticated score-only use and an explicit parent keep action extend it, and how offline play is treated. A parent needs a current verified reachable contact, a workable warning process and sufficient notice. As a proposed design, begin warnings at least 30 days before the three-year anniversary, but do not treat that interval or successful inbox delivery as already established. Failed, bounced or uncertain delivery and unknown activity must prevent automatic deletion. Any later deletion job must lock/recheck the exact child relationship and activity, preserve deletion-journal and restore protections, and coordinate parent-form and backup retention. Those components are not implemented here.
