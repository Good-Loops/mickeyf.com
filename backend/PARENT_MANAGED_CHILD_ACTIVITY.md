# Parent-managed child activity

This source feature is default-off. The SQL draft is outside the migration manifest. No migration, backfill, warning or deletion is performed by this document. Before activation, review the draft, exact target and rollback. The runtime account requires table-level SELECT on the two-column activity table (so schema inspection sees every column) and column-scoped INSERT on both columns and UPDATE on `retention_activity_at`. Startup refuses an absent or altered table, extra checks or triggers, and insufficient privileges. `CHILD_ONLINE_ACTIVITY_ENABLED=true` explicitly activates the backend only after the child-audience, signed-form and journaled-deletion prerequisites; `VITE_ENABLE_CHILD_ONLINE_ACTIVITY=1` separately enables the foreground client and parent keep button. Both must be verified on each actual shipped client before any retention enforcement.

For newly created managed child accounts, the creation transaction initializes one UTC timestamp. Successful password sign-in, an accepted game submission including a non-best p4-Vega score, and trusted foreground online input advance it monotonically. No raw interaction history is retained. The foreground reporter is throttled to at most once per hour on user input, never on an idle timer or passive session renewal. It makes one initial report per authenticated untracked session and then stops. A signed-in parent may keep a currently linked child account active; this advances the same timestamp. Failed transactional writes roll back creation, sign-in or scores. Missing rows are never guessed or backfilled and must remain on hold.

Online reports cannot observe offline-only activity, native/embedded gameplay input that the foreground page cannot see, or activity during outages. A successful report is not proof that all previous activity was observed. Production enforcement needs independently monitored continuity, validated browser and native game coverage, a recovery or hold policy for outages, parent-facing disclosure, a working parent warning/keep workflow, and reliable verified warning delivery with adequate notice. A timestamp alone is not sufficient to delete: a separate lifecycle must lock and recheck the exact parent-child relationship, activity and warning, and preserve deletion-journal and restore protections. Those lifecycle components are not supplied by this activity foundation.
