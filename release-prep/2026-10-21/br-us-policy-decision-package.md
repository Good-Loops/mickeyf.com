## Current primary-source findings

The amended COPPA operator requirements already apply: ordinary compliance was
due 22 April 2026. A parent-signed form returned by electronic scan is expressly
listed; reasonable efforts to establish parental authorization still apply.
[Final rule dates](https://www.govinfo.gov/content/pkg/FR-2025-04-22/html/2025-05904.htm),
[16 CFR 312.5](https://www.ecfr.gov/current/title-16/chapter-I/subchapter-C/part-312/section-312.5).
Public notice must describe purposes, retention need and deletion timeframes;
indefinite retention is not allowed. The written security program must include
coordination, annual risk/program review, safeguards/testing and relevant provider
assurances. The accompanying [draft program](security-retention-program.draft.md)
is not evidence that these actions happened.
[312.10](https://www.ecfr.gov/current/title-16/chapter-I/subchapter-C/part-312/section-312.10),
[312.8](https://www.ecfr.gov/current/title-16/chapter-I/subchapter-C/part-312/section-312.8).

Brazil's ECA Digital applies from 17 March 2026 to directed or likely-accessed
products. Assess arts. 12–18 and the proportionality in art. 39 for the actual
product: age signals, risk information and Portuguese parental controls, including
time/usage mechanisms where applicable. Do not assume a custom usage tracker is
mandatory or that a link to OS controls automatically satisfies the duties.
Do not add child telemetry merely to fill a review box.
[Lei 15.211/2025](https://www.planalto.gov.br/ccivil_03/_ato2023-2026/2025/lei/l15211.htm).

## Concrete retention operation to qualify

The existing maintenance path runs `cleanupSignedParentForms`; it deletes expired
unused SQL rows. It does not remove messages or files. Child deletion can cascade
the form row. The current account UI lists unused unexpired requests, so it is not
a complete retention inventory. A child can be created and deleted between two
operator visits without ever appearing as active in that inventory.

Use a **private encrypted copy** of the [synthetic register template](parent-form-retention-register.example.csv).
Required content is only the request reference, receive/expiry/decision times,
file digest, opaque message/file locators, reconciliation and deletion completion.
No child name/nickname/password, birth date, identity document or provider token.
The reference and locators are still protected personal metadata. Add an account
identifier only if necessary for an approved reconciliation purpose.

Proposed twice-weekly procedure, pending owner acceptance and demonstration:

1. Record each received attachment and its request reference privately. Use the
   existing exact review checks; the register does not grant permission.
2. Reconcile every retained reference across **all statuses**, including used and
   expired. Use the read-only report described below. A successful zero-row lookup
   is different from a timeout or failed lookup; `inspect` failure alone cannot
   prove absence. Qualify the actual report/register pass before launch.
3. Delete rejected/incomplete material promptly, within the published 14-day
   limit. For approved-but-unused forms, propose deletion at the first pass after
   expiry/cancellation; this missing case needs final notice wording and approval.
4. Retain a used form only while its account-consent evidence remains necessary.
   Reconcile withdrawals/deletions with the private reference. Purge missing or
   cascaded request material promptly in that pass, rather than starting another
   14-day clock on discovery. Investigate an unexpectedly missing form for a
   known still-live child; do not infer consent or silently reapprove it.
5. Cover inbox/archive/sent/trash, downloaded and synced copies and recovery
   arrangements. Record completion without retaining another attachment. Decide
   a justified finite completion-record period. Provider recovery handling must
   be described accurately; do not promise physical erasure everywhere in 14 days.
6. A failed reconciliation leaves the record unknown. Resolve it promptly; if
   the review/deletion workload cannot meet the agreed schedule, keep new child
   creation closed while catching up. No automated mailbox deletion is installed.

Acceptance rehearsal: synthetic rejection, approved-unused expiry/cancel, used
account withdrawal, create-and-delete-between-passes, failed lookup, all-copy
deletion and restore/replay handling. Keep private proof of the operation; no
real child material is needed in repository evidence.

### Read-only reconciliation command

`parent-form:retention` accepts only a private stdin object with `references`,
containing 1–100 unique request UUIDs. No input file path, attachment, message body,
nickname or password is accepted. Example input is synthetic:

```json
{"references":["00000000-0000-4000-8000-000000000001"]}
```

The operator must use the clean frozen checkout, existing authenticated loopback
proxy and explicit administrative confirmations described in the
[schema-operation guide](../2026-10-20/child-schema-operation.md). Source commit,
server/database/account, exact history, schema and grants are verified. The
bounded session performs SELECT/SHOW only and emits the complete result only
after checks succeed. It does not approve a form or delete any record/file/mail.

```powershell
# Private files outside the checkout, after authorization for the actual target.
Get-Content -Raw C:\private-release\retention-references.json | npm --prefix backend run --silent parent-form:retention > C:\private-release\retention-report.json
```

Report states are `pending`, `approved`, `rejected`, `expired-unused`, `used` and
`not-found`. A `used` row remains used after its original request expiry; it is
not a fresh consent approval. `not-found` means only that the successful lookup
found no row for that exact reference at that time. An error produces no complete
report; never treat it or an old report as proof of account deletion. No contact,
parent/child account identifier, nickname, signature or credential is output.
Keep reports private and retain them only for the adopted operational purpose.
Large private registers require deliberate bounded batches; this is not a full
database inventory or an automatic deletion scheduler.

Source: [observer](../../backend/ts/accounts/signedParentFormRetention.ts) and
[CLI](../../backend/ts/accounts/runSignedParentFormRetention.ts). Local validation
passed: `npm --prefix backend test`, all 1,021 tests from
`npm --prefix backend run test:unit`, and nine real disposable MySQL cases from
`node backend/scripts/run-child-schema-tests.mjs`, with scoped cleanup confirmed.
The ten focused report/CLI tests are included in the full suite. The real SQL
cases include legacy/extended schemas, every report state, a child-deletion
cascade and failed lookup. Independent review found no remaining concrete issue
in this bounded tool. No production report or real parent-form operation ran.
