# Isolated native device validation

The native session bridges pin their backend host. Staging builds must therefore be built separately; changing the web URL alone is not sufficient. The Android staging build has package ID `com.mickeyf.app.staging` and a distinct launcher label. The iOS staging build requires bundle ID `com.mickeyf.app.staging`, the `DEBUG` and `LUDOLUME_STAGING` Swift conditions, and a development signing profile. Release builds keep the production host. The staging build accepts only its exact configured HTTPS host and the existing method/path allowlist. A missing or invalid host fails closed. The operator must independently verify that the selected hostname actually reaches an isolated backend; a hostname suffix cannot prove this.

One zero-cost candidate is a local synthetic-only backend with a temporary local MySQL database and a Cloudflare Quick Tunnel. The repository's `compose.migration-test.yaml` demonstrates an isolated local MySQL setup; the default `compose.yaml` connects to Cloud SQL and is not suitable. Quick Tunnels are public to anyone who knows the URL, terminate HTTPS at Cloudflare and change hostname on restart. They require no inbound port forwarding, but require accepting the service's trust and terms. Restrict the test service to synthetic data, no production credentials, real emails, real child data or enabled external providers; enforce access controls suitable for a noninteractive API, and shut it down afterward. Verify that the backend uses only the isolated database and a non-sending email adapter before any test. Do not create a tunnel or deploy a backend solely on the basis of this note.

Once a backend is qualified, build the frontend with `VITE_PROD_API_URL=https://<exact-staging-host>` and sync the native project. For Android, use a quoted `-PludolumeStagingHost=<exact-staging-host>` with the `assembleStaging` task; the property may name only a non-production Cloud Run or Quick Tunnel hostname. Install the resulting debug-signed staging APK on the owner's connected Android device. For iOS, set the exact hostname in the `LUDOLUME_STAGING_API_HOST` Xcode build setting, set `PRODUCT_BUNDLE_IDENTIFIER=com.mickeyf.app.staging`, and build a Debug configuration with `SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG LUDOLUME_STAGING"` under a valid development profile. This Windows workspace cannot compile or sign iOS locally; the existing TestFlight workflow builds Release and cannot serve as this staging build. Confirm the full Vite and native host settings match: mismatch is rejected. Never distribute staging builds as release candidates.

For each device, record app build and backend revision, test account identifiers, and the synthetic clock. Verify guest play, login, parent/child flow, activity reset, warning and delivery to a synthetic sink, no deletion before the required deadline, retention or cancellation when activity resumes, eventual deletion only after all prerequisites, and retry/idempotency using the agreed policy. Run clock advancement only in isolated tests; do not alter production clocks or records. Verify age-signal unavailable/denied/shared behavior separately if supported. Inspect the resulting synthetic database state and cleanup. This tests the debug build and isolated backend, not real Apple/Google identity, email delivery, production routing, or the store-delivered release.

For release acceptance, independently build the exact reviewed source with production settings, install iOS through a current signed TestFlight build and Android through Play's appropriate track, and verify provider callbacks, login, guest play and permissions on the actual devices. App Store and Play console status, submission readiness, Google closed-testing eligibility and physical device results require their own current checks. A debug APK does not establish the Play signing identity. Track iPad acceptance separately when iPad distribution is enabled.

References: [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), [Apple developer account and on-device testing](https://developer.apple.com/help/account/basics/about-your-developer-account), [Android command-line device builds](https://developer.android.com/build/building-cmdline).
